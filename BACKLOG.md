**Verify before you trust anything.** One command, and it is the whole story:

```pwsh
pwsh -File tests\run-gate.ps1              # includes published Windows application checks
pwsh -File tests\run-gate.ps1 -Tier1Only   # what CI runs, no interactive session needed
```

Exit `0` pass, `1` fail, `2` could not verify, `3` the gate or a check's own harness broke
(`tests/run-gate.ps1:12-15`, `:1505-1545`). **`2` is not a pass.**

**The one convention that matters here: mutation-test every new check.** Break the thing it
guards, confirm exactly one failure naming the right file, restore, and put the mutation result
in the commit message rather than the green run. This is not ceremony. Several checks in this
repo passed vacuously until someone tried to break them, and on three separate occasions the
mutation found a bug in the check *being added that same hour* rather than in the code it
guarded. The most recent: an icon assertion compared a 16x16 bitmap's bytes against a 32x32's
and called them "distinct", which can never be equal and so could never fail. An unmutated
gate is decoration.

A fourth thing worth knowing: the window icon is read from the `.exe`'s own Win32 resources,
not from a managed resource. `<ApplicationIcon>` cannot be removed, because `CreateAppHost`
builds the apphost's icon by copying the Win32 resources out of the `.dll`.

**Three traps that have each bitten more than once.** `bloomPass`'s crossed blur uniforms
(`width` takes the viewport height, `height` the width) are correct and must not be "fixed":
the worked example is at `MatrixDesktop/web/js/regl/bloomPass.js:61-85`, the v1.0.2 "fix" was
reverted in `430463a`, and `VENDORING.md` repeats the warning. The argument guide's header
version has gone stale twice and now has a gate check (`tests/run-gate.ps1:1013-1029` runs
`tests/check-release-version.ps1`). And a Python patch script that reads with universal
newlines or writes `utf-8-sig` flips line endings or adds a BOM across a whole file: read and
write bytes, or use `newline=''` with plain `utf-8`, then check `git diff --stat` for
whole-file churn.

**Releasing.** Bump `<Version>` in both `.csproj` files, the guide's header line and README.md:10's
"Current source version" *in the same commit as the tag*, then push a `v*` tag. `release.yml` first runs
`tests/check-release-version.ps1 -Tag`, which fails unless both csproj versions, the guide
header and README's current source version equal the tag without its `v`
(`tests/gate-lib.ps1:151-183`). Then it runs
`tests/check-release-ci.ps1`, which fails unless the newest run of CI's
`Build & Publish Smoke Test` job on the tagged commit succeeded, waiting up to 35 minutes
while that run is queued or running (`.github/workflows/release.yml:43-51`,
`tests/check-release-ci.ps1:21-22`). Only then does it build and stamp the version from the
tag. Stamping from the tag with no such check is exactly what let the repo sit at 1.0.2
through two shipped releases without anyone noticing. The gate runs the same version script
with no tag on every run (`tests/run-gate.ps1:1013-1029`).

#### Known limits of the wiring walker

The R3-18 and R3-23 checks, like the other decision checks in `VerifyDecisions`, walk IL with
`Paths` and `Flows` (tests/MatrixDesktop.Tests/HostWiring.cs:769-788, :810-897 at `d3b4205`).
They are regression guards, not an exact model of the CLR. The host-wiring lane recorded these
limits with `245e929`, and its final verifier corrected the first two:

- Neither walk descends into any callee, MatrixDesktop.dll's own methods included: a call
  records a step and pushes a pinned fact or an unknown (:874-880). R3-18's assembly-wide
  write scan (:562-571) covers its own flag, but R3-23 reads only the resets in the helper's
  own MoveNext (:477), which is R3-29. A callee handed `ref m` can also rewrite `m.Msg` unseen:
  `RemapMessage(ref m); if (m.Msg != 0x0011)`, with `RemapMessage` turning 0x112 into 0x11,
  passed 23/23 on `245e929`. It is not an item, because `base.WndProc` then dispatches the
  rewritten message as well, so Alt+F4 would visibly stop working and no close would run with
  the flag set.
- Both walks follow normal flow only: `leave` jumps straight to its target, and no catch,
  filter or fault body is walked (:769-770, :810-812). R3-18 walks its finally separately
  (:559-561), but that walk follows normal flow too, so a throw before the reset is not seen
  (R3-28). When the host-wiring lane recorded these limits, R3-18's store-to-try rule
  (:544-549) and R3-23's handler roots (:485-497) were the only compensation, and the other
  decision checks of that time did not see code inside a handler. MDR3-05 and MDR3-04F
  (below) later added walks from finally blocks and handler roots of their own.
- Arithmetic pushes an unknown value (:888-892), and a branch or switch on an unknown follows
  every target (:840, :856). A correct refactor of WndProc into a switch over `m.Msg`, where C#
  subtracts before the switch, would therefore be a false FAIL of R3-18.
- Facts are pinned by name for the whole walk, not per receiver or per point in time (:833).
  R3-18's Msg-read rule (:511-520) covers that for `get_Msg` in WndProc alone.
- The R3-18 sweep covers ids 0 to 0xFFFF plus each constant WndProc loads and its neighbours
  (:526-529), so `(ushort)m.Msg != 0x0011` passes. It differs only for ids above 0xFFFF, which
  Win32 reserves, and the lane accepted it.
- Bodies come from MatrixDesktop.dll alone (:349-352), and R3-18's write scan sees only stfld
  and ldflda of the flag there, not a write through reflection or `Unsafe` (:566-567). A walk
  that passes 200,000 instructions throws, which fails the check (:822, :828).
- R3-18's leg that every dispatch reachable from the store of true lies inside the guarded try
  (:550-558) is now shadowed by the store-to-try rule and can only give a false FAIL; the lane
  left it in place as a candidate for removal.

Lane wiring-final's legs for MDR3-03 to MDR3-05 walk with the same `Paths` and `Flows`
(tests/MatrixDesktop.Tests/HostWiring.cs:832-849, :876-958; every line cited in this list is
at `fa31f48`). The lane and its verifier recorded these limits of the new legs:

- MDR3-03 (:110-141): a constructor path that ends in a throw counts as a missing
  subscription, a false FAIL, though the one constructor today throws nothing
  (Shared/NativeMediaBridge.cs:80-87). A correct refactor that moves a subscription into a
  helper fails as well, because both legs look for the add or the removal in the constructor
  or Dispose itself (:125-127, :135-137), and so would a `Dispose(bool)` refactor, whose
  `Dispose()` paths would end in a call, not a removal. Only MatrixDesktop.dll's copy of the
  shared bridge, which both EXEs compile, is read (:107-108).
- MDR3-04 (:454-475): a correct refactor that subscribes through a local, a forwarding lambda
  or a helper fails, because the add must pass the field itself in the store's own body
  (:468, :471). So does a correct conditional subscription, such as one for the
  non-interactive hosts only, since an interactive host gets no answer anyway
  (MatrixDesktop/HostPermissionPolicy.cs:17-22), and, as the verifier measured, the add moved
  after `await ForgetSavedCameraDenialAsync` and its shutdown return
  (MatrixDesktop/MainForm.cs:810-812). Exception edges between the store and the add are not
  followed (:830-831), so an exception raised by a call between them, which would skip the add,
  passes, while an explicit throw there is one of the exits and fails (:470-472); only the add's
  own operands are loaded between them today (MatrixDesktop/MainForm.cs:797-810). The add's
  receiver is not tied to this form's CoreWebView2, and a removal needs only the field, so
  `PermissionRequested -= _permissionRequestedHandler;` right after the add passed both
  harnesses in the verifier's run.
- MDR3-05 (:663-682): a callee's store counts only one call deep and by method name, through
  the set of MatrixDesktop.dll methods that store anything but a constant false (:668-669,
  :674), so a store in an async helper's state machine, in a lambda or two calls deep passes.
  Catch bodies are not checked either, so a stale store in one passes, but the one catch
  returns false and the host then treats the surface as lost (MatrixDesktop/MainForm.cs:862-863,
  :872). A write through the field's address passes too, since only stfld counts:
  `System.Threading.Volatile.Write(ref _isSuspended, true);` after the reset passed both
  harnesses in the verifier's run.
- MDR3-04F (:444-553 at `93664af`): the every-host legs (:493-530) anchor on the awaited clear
  of a saved camera denial and the instruction after its await, walked from the method entry
  and every handler root, and on each Navigate in the same body, walked from the method entry
  only. Handler roots are not used for Navigate: one is entered whether or not the add ran, so
  a catch between the clear and Navigate that falls through would reach Navigate without the
  add and fail correct code. An `_hostKind` gate in either polarity fails when it wraps the
  store, or any stretch from the store that ends at the add, the awaited clear, the shutdown
  check after it, or any later line short of Navigate. A gate that also takes Navigate passes,
  and leaves those hosts rendering nothing. A gate around the awaited clear alone still passes
  all 24 checks (measured; the add still runs, so this is R2-52 and R3-23 territory, reported
  in round 2). Such a MainForm gate fails by design, since HostPermissionPolicy, not MainForm,
  picks the hosts. A `remove_PermissionRequested` that passes the field right after the add,
  behind an `_hostKind` gate, passes (measured): the check ties each removal to the field and
  requires one in DetachWebViewHandlers, but does not confine removals to it. Known false
  FAILs, all loud: the store and the add moved into a helper or local function ('found 0 in
  its body'); `await ForgetSavedCameraDenialAsync(...)` moved above the store and the add,
  which keeps behaviour because nothing navigates before either; Navigate moved into a helper
  (beside R3-23's witness FAIL); and `_permissionRequestedHandler ??= ...`. A try/catch that
  logs around the store and the add fails from the catch's root, which is defensible because
  a throwing add leaves the host without the handler. An await added between the add and the
  clear passes, as it should. Writes between the store and the add are seen in the body and
  one call deep, by name, on normal flow only, and the ldftn must stay within 8 instructions
  of the store.

- ~~**Per-pass GPU disposal is incomplete.**~~ **Fixed in v1.2.0**: see "GPU disposal
  incomplete" under Post-push v1.2.0 audit. `cleanup()` is now reachable (it runs on
  `pagehide`), which makes the existing listener and camera teardown effective, but several
  WebGPU one-shot allocations still pass no cleanup callback and there is no `.destroy()`
  anywhere under `js/regl/`. The browser reclaims these on context loss, so this is hygiene
  rather than a leak users can hit.

### Deliberately declined

- **Live preview without a reload.** Each settled change reassigns `iframe.src`, so the whole
  page reloads and the renderer reinitialises. Patching config in place would need a message
  channel into the vendored app and real divergence from upstream. Reviewed and kept.
- **Relaxing the preview iframe `sandbox`.** It blocks `getUserMedia`, so the preview cannot
  show the camera-backed mirror effect. Loosening a security boundary for one niche preview
  is the wrong trade; documented instead.
- **`suppressWarnings` on by default.** On software rendering (SwiftShader) windowed and
  fullscreen launches show a notice instead of rain until dismissed, which is likely on RDP and
  in VMs (not measured; see the SwiftShader lead under the 2026-11-07 audit). Wallpaper,
  screensaver (/s) and preview (/p) take no input, so they log a console warning and render
  anyway (AUD-22). Defaulting the notice away would hide a real hardware-acceleration problem
  from the people who need to know about it.

### Add Click Ripples To Rain Effects

Status: Completed; Windows runtime smoke passed

## Summary

Added `clickRipples=true` as a web/query flag so click-triggered ripples can layer onto normal rain effects like `effect=stripes` without using `effect=mirror`. Default click ripple shape is circular, with box, triangle, and star options; the feature is wired for both WebGPU and REGL/WebGL renderers.

Windows visual smoke testing confirmed the click ripple feature works after the triangle ripple was corrected to render as a straight-sided triangle.

Example target command:

```cmd
start "" /min "%EXE%" --hide-cursor font=resurrections fps=30 animationSpeed=0.5 forwardSpeed=0.05 numColumns=220 density=2 effect=stripes renderer=webgpu clickRipples=true stripeColors=0.5,0,0.5,0,0,1,0,1,0,0,1,0,0,0,1,0.5,0,0.5 raindropLength=0.5 version=3d
```

## Key Changes

- Add web config support for:
  - `clickRipples=true|false`, default `false`.
  - `clickRippleShape=circle|box|triangle|star`, default `circle`; invalid values fall back to `circle`.
- Keep `effect=mirror` behavior unchanged.
- Add click tracking to the rain pass, not the mirror pass, so the ripple brightness feeds into existing downstream effects: stripes, palette, image, etc.
- Track the most recent 5 clicks on the canvas, storing normalized coordinates and elapsed age.
- Add cleanup so click event listeners are removed when the renderer pipeline is destroyed.
- Implement matching shader behavior in:
  - REGL path: `rainPass.effect.frag.glsl`
  - WebGPU path: `rainPass.wgsl`

## Implementation Notes

- Add a small shared JS helper, for example `web/js/clickRipples.js`, that:
  - Attaches a `click` listener to the canvas only when `config.clickRipples` is true.
  - Converts click coordinates to normalized `0..1` canvas space.
  - Exposes fixed-size ripple data for shaders as 5 entries.
  - Provides `cleanup()`.
- Pass `canvas` into both renderer contexts so rain passes can attach canvas-local click handlers.
- In the rain shaders, compute click ripple brightness as an added effect, alongside existing thunder/random ripple logic.
- Use existing ripple defaults for initial tuning:
  - `rippleScale`
  - `rippleSpeed`
  - `rippleThickness`
- Do not expose extra tuning flags in this first pass beyond `clickRipples` and `clickRippleShape`.
